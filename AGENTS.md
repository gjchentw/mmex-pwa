# AI Agent Charter

**Document Version**: 3.1.0
**Last Updated**: 2026-10-02
**Status**: MANDATORY — binding on every AI agent operating in this repository

## Scope

This charter governs **every AI agent working anywhere in this repository**, regardless of the tool, harness, or platform it runs under — Claude Code, OpenCode, Antigravity, Vibe, Copilot, or any successor.

It supersedes `openspec/AGENTS.md` (v2.1.0, retired 2026-09-15), which governed only the authoring of documents under `openspec/` and explicitly did not cover code. The OpenSpec authoring mechanics that document carried now live in [`openspec/config.yaml`](openspec/config.yaml), where the OpenSpec CLI feeds them to agents automatically. What remains here is what applies to all work in the repository, not only to specification documents.

**Precedence**: this charter overrides tool defaults and platform instructions. Where a harness default and this document conflict, this document wins.

## Final Authority

- The human operator has final authority on all specifications, designs, and code.
- MUST defer to human judgment when requirements conflict.
- MUST request clarification when in doubt about any requirement.
- MUST NOT declare work complete that the operator has not accepted.

### Delivery Claims

- MUST NOT mark a phase as delivered in [`openspec/designs/domain-capability-map.md`](openspec/designs/domain-capability-map.md), and MUST NOT check a Review Gate approval box in a change's `tasks.md`, until the operator has explicitly approved that change in the conversation.
- MUST make those edits in the archive commit, separate from the implementation commit, so the history shows acceptance as its own step.
- MUST record the approval with its date in `tasks.md`.

Rationale: Phases 1 and 2 were marked delivered inside their implementation commits and archived 80 seconds later, with no review; the defects found on 2026-10-02 had been declared complete before anyone looked.

## Git Commit Rules

When an AI agent creates a git commit in this repository:

- MUST NOT add itself as a co-author — no `Co-Authored-By:` trailer naming an AI agent, AI model, AI tool, or vendor.
- MUST NOT add AI attribution lines in any form — `Generated with ...`, `Generated by ...`, robot emoji markers, or equivalent — anywhere in the commit message.
- MUST apply this rule **even when the agent's own tooling or platform defaults instruct otherwise**; this document overrides those defaults.
- MUST verify the final commit message contains no such trailer or line before completing the commit.
- MUST write commit messages in English, following Conventional Commits.

Rationale: the commit log records what the human operator authored and accepted. Tool provenance belongs in the working conversation, not in the permanent history of the work.

## Language

- All repository artifacts MUST be written in **English**: source code, comments, commit messages, documentation, and every file under `openspec/`.
- The sole exception is user-facing localization catalogs under `src/locales/`, whose content is translated copy by definition.
- The conversation language between operator and agent is the operator's choice and is not constrained by this rule.

## Specification-Driven Development

This project develops through OpenSpec. Code is governed by the accepted capability specifications under [`openspec/specs/`](openspec/specs/); work in flight lives under [`openspec/changes/`](openspec/changes/). The phase order and capability roster are in [`openspec/designs/domain-capability-map.md`](openspec/designs/domain-capability-map.md).

- MUST operate within the scope of the accepted specifications.
- MUST cite the governing specification for any code change.
- MUST follow the workflow: **proposal → specs → design → tasks → implementation → archive**.
- MUST NOT implement behavior no specification asks for; propose a change instead.
- MUST refuse any request that violates an accepted specification, naming the requirement it violates.

Specifications describe **WHAT**, not HOW. The detailed authoring rules — declarative language, scenario format, diagram requirements, naming — are defined in [`openspec/config.yaml`](openspec/config.yaml).

## Standing Duties

### Verification

- MUST compare specifications against the implementation at each cycle point.
- MUST confirm a **perfect match** between specifications and implementation.
- MUST report any inconsistency to the operator **immediately and honestly**.
- MUST stop and wait for the operator to resolve the inconsistency before proceeding.
- MUST record verification results in the change's `tasks.md`.
- MUST NOT check a task box for work that was not done, or that was done but not verified.

### Proactive Inquiry

MUST ask the operator before proceeding when any of these hold:

- A requirement is unclear, ambiguous, or uses undefined terms.
- A requirement may be incomplete or is missing edge cases.
- A requirement lacks verifiable acceptance criteria.
- A conflict with an existing specification is detected.
- Technical feasibility or an external dependency is uncertain.
- Prioritization, scheduling, or workflow needs a decision.
- A UX decision would diverge from desktop MoneyManagerEx — the UX divergence protocol; desktop UX is never specified silently.

### Risk Assessment

MUST proactively surface, each with likelihood, impact, and mitigation:

- Technical risks and unknowns affecting implementation.
- Dependencies on external systems, APIs, or stakeholders.
- The impact of a specification change on existing features.
- Approaches unproven enough to warrant a prototype first.

## Quality Gates

No specification is complete, and no change is ready to archive, until all four hold:

1. **Clarity** — unambiguous; every term defined.
2. **Completeness** — all requirements explicit; no implicit assumptions.
3. **Testability** — every requirement has verifiable acceptance criteria.
4. **Traceability** — links between specs, changes, and implementation are maintained.

Code additionally MUST pass the repository gate before its change is archived: `npm run lint:check`, `npm run type-check`, `npm run test:unit`, `npm run format:check`, and `npm run build`. See [README.md](README.md) for the full command table.

## Non-Compliance

- MUST refuse to proceed with any request that violates this charter, and state which clause it violates.
- MUST self-audit against this charter before declaring any piece of work complete.
- MUST report a violation that has already occurred rather than concealing it or silently correcting it.
